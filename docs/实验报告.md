# 增量知识图谱更新实验报告

基于CRTM真实GTFS数据的全量重构与单线程增量更新对比实验（对应论文表1前两行）

## 1. 实验概述

本实验按照《README》指导，在真实数据上复现并测量两种知识图谱更新方式的成本：

- **全量重构**：变更到来后对整份数据从头执行一次RML映射；
- **单线程增量更新**：diff旧新快照 → 仅映射变更行 → 按IRI模板计算待删除实体 → 从既有图谱中删除旧行quad、并入新quad。

每种方法在5个独立seed（同一基准数据`data/before`，各自独立施加10%变更）上重复，报告均值±标准差。并行增量方法按指导约定另行实现，不在本实验范围内。

## 2. 实验环境与数据

| 项目 | 内容 |
|---|---|
| 系统 | Ubuntu 20.04，16核，15 GiB RAM |
| Java | OpenJDK 21.0.7 |
| RMLMapper | 8.1.0（复用旧实验目录中的jar） |
| Python | 3.13.12（rdflib 7.6.0，仅用于辅助脚本） |
| 数据 | CRTM马德里地铁GTFS（12个标准文件），`stop_times.txt` 2216行、`shapes.txt` 57474行、`stops.txt` 1050行、`trips.txt` 120行 |
| 映射 | GTFS-Madrid-Bench风格的RML映射（13个TriplesMap，12个标准R2RML join，0个blank node） |
| 变更 | 每seed对`stop_times.txt`独立施加10%变更：insert=55、update=55、delete=55、composite=57 |
| StopTime IRI模板 | `http://transport.linkeddata.es/madrid/metro/stoptimes/{trip_id}-{stop_id}-{arrival_time}` |

每个StopTime实体映射出6条quad（type/stopSequence/arrivalTime/departureTime/stop/trip），全图共375,546条。

## 3. 实验流程

1. 下载真实GTFS → `data/before`（作为5个seed共同基准，之后不再改动）；
2. `change_generator.py`以seed=1..5独立生成5份变更快照`data/after_seed{1..5}`及变更日志；
3. `run_full_reconstruction.sh`对5份快照各做一次全量重构，`/usr/bin/time -v`记录耗时/内存；
4. 对`data/before`构建一次baseline图谱（不计入任何方法的耗时），`find_iri_template.py`确认StopTime的IRI模板；
5. `run_incremental_update.sh`对5个seed执行增量更新，记录端到端耗时；
6. 正确性校验：每个seed的增量输出与该seed数据的全量重构输出做`sort`+`diff`逐行比对；另按指导第5节用独立的verify全量运行复核seed1。

## 4. 实验过程中遇到的问题与解决（重点）

实验中遇到的问题分为四层：数据层、映射适配层、增量链路设计层、实现细节层。以下按"现象 → 根因 → 影响 → 解决 → 验证"逐条记录。

### 4.1 数据层

#### 问题1：数据门户不可达

- **现象**：指导给出的下载入口 `datos.crtm.es` 在当前网络环境下TLS握手被代理中断（`SSL_ERROR_SYSCALL`），网页与API均无法访问。
- **解决**：该数据集同步发布在ArcGIS Hub，改走 `www.arcgis.com/sharing/rest/content/items/{id}/data` REST接口，成功下载同一数据集（1.5 MB zip，12个文件，内容为标准GTFS结构）。
- **影响评估**：数据内容一致，仅分发渠道不同，不影响实验有效性。

#### 问题2：全部文件带UTF-8 BOM

- **现象**：12个CSV文件头3字节均为`EF BB BF`。
- **风险**：BOM会并入首列列名（如首列变成`\ufefftrip_id`），导致映射中对该列的引用失配。
- **解决**：入`data/before`前统一去除BOM（`sed -i '1s/^\xEF\xBB\xBF//'`），并逐文件复核确认清除。

### 4.2 映射适配层

#### 问题3：mapping的数据源文件名与真实GTFS不匹配

- **现象**：现有mapping引用的是VIG生成器的大写`.csv`命名（`STOP_TIMES.csv`等），真实数据是小写`.txt`；`normalize_mapping.py`按精确文件名解析会直接`FileNotFoundError`。
- **解决**（经确认）：给`normalize_mapping.py`加兜底——精确名找不到时按"去扩展名+忽略大小写"匹配唯一候选；多于一个候选或零候选则报错终止，不做猜测。
- **核对**：mapping引用的全部列名与真实数据列名逐一比对完全一致，因此只需修文件名解析，无需另找映射。

#### 问题4：mapping使用了未声明的前缀

- **现象**：mapping正文使用`rdf:type`（13处）但头部没有`@prefix rdf:`声明，rdflib解析报`Prefix 'rdf:' not bound`。
- **决策依据**：指导文档明确警告过此类问题——只允许对rdf/rdfs/xsd/owl这类确凿无疑的标准命名空间自动补声明，禁止对陌生前缀瞎猜URI。
- **解决**：在mapping.ttl头部补一行标准的rdf前缀声明。

#### 问题5：RMLMapper不识别`.txt`扩展名的数据源

- **现象**：归一化后的映射把数据源指向`xxx.txt`，RMLMapper启动即抛`Unrecognised content type: text/plain`。
- **根因**：RMLMapper按文件扩展名推断数据源内容类型，`.txt`不在支持列表（最小对照实验证实：同一映射指向同内容的`.csv`正常输出，指向`.txt`必现该错误）。
- **解决**：`normalize_mapping.py`在解析出的源文件扩展名不受支持时，在数据目录的隐藏子目录`.csv_mirrors/`下创建`<stem>.csv`软链接并引用之。镜像放隐藏子目录是为了不污染数据目录、不与`compute_delta.py`的`*.txt`glob和stem匹配产生歧义。
- **此决定的遗留隐患**：见问题11（软链接被copytree解引用导致陈旧镜像），这是本次实验最隐蔽的一个bug。

#### 问题6：mapping含12个join，超出指导脚本的前提

- **现象**：`grep -c "joinCondition\|parentTriplesMap"`得24（12个join），不满足指导第0节"两个都为0才适用"的前提。
- **分析结论**（经确认采纳）：R2RML规范保证`rr:parentTriplesMap+rr:joinCondition`只能产生"指向父实体自身IRI"的引用三元组，对象值由父表主键列唯一决定。逐一核验12个join均为标准写法（`rr:child`+`rr:parent`+父TM subject模板变量仅由join列构成）。由于`change_generator.py`只改`stop_times.txt`的非主键时间列、且不存在其他TriplesMap从`stop_times`反向取值，父表在本实验中永远不变，故**不需要fan-out算法**，指导脚本架构成立。
- **附带验证**：`stop_times`对`stops`/`trips`的引用完整性实测为0悬空（272个stop_id、120个trip_id全部存在）。

### 4.3 增量链路设计层

#### 问题7：照指导原样执行，增量输出会产生大量重复quad

- **现象推演**（后经实证）：`compute_delta.py`先把after全部文件复制进delta_dir再覆写有变更的文件，于是未变更文件以完整副本留在delta_dir；`run_incremental_update.sh`对delta_dir跑**完整mapping**，未变更实体（包括57k行的shapes）被重新映射输出；`apply_delta_to_graph.py`直接拼接baseline与delta，未变更实体的quad出现两份。RMLMapper单次运行内部会去重（已实测），但跨文件拼接不去重，指导第5节的`sort`+`diff`校验必然失败。
- **连带问题8**：完整mapping里存在`shapes`(57,474行)→`shape_points`(57,474行)的join，RMLMapper的join是朴素实现，约3.3×10⁹次比较，单次全量映射约30分钟。增量运行若也跑完整mapping，耗时与全量几乎相同，表1第二行失去意义。
- **解决**（经确认采纳）：新增`build_delta_mapping.py`，从完整mapping提取stoptimes专用delta映射——只保留`map_stoptimes_0`，并把它的2个join替换为等价的`rr:template`对象映射（显式`rr:termType rr:IRI`）。替换的等价性前提逐一验证：①join是标准R2RML形式；②父TM subject模板变量仅由join列决定；③引用完整性无悬空（否则join不发三元组而模板会发，二者才有差异）。`run_incremental_update.sh`的RMLMapper步骤改用该专用映射。
- **等价性实证**：真join版（stoptimes+stops+trips三个TM，保留真实join）与模板版在同一数据上分别映射，stoptimes实体的quad集合**完全一致（13,296条，双向差集为空）**；耗时分别为4.1s与1.8s。
- **效果**：增量映射只处理真正变化的167行，毫秒级完成；重复quad问题随之消失（delta_dir中未被专用映射引用的文件不再产生任何输出）。

### 4.4 实现细节层

#### 问题9：IRI百分号编码不一致，删除操作全部落空

- **现象**：首次增量运行`removed(按subject)=0`——167个待删除IRI一个都没匹配上。
- **根因**：RMLMapper生成模板IRI时做百分号编码（时间值`01:05:17`进入IRI变成`01%3A05%3A17`），而`compute_stale_iris.py`按原始字符拼接，两边字符串永不相等。
- **解决**：`compute_stale_iris.py`增加`iri_encode()`：RFC 3986非保留字符（字母/数字/`-._~`）保持原样，其余按UTF-8大写十六进制`%XX`编码。实测标定：本数据中仅`:`被编码为`%3A`，`_``-``.`保持原样，与新规则的行为完全吻合。
- **修复后**：removed=1002（167个旧实体×6 quad），与delta_added对称。

#### 问题10：change_generator插入操作可能生成冲突主键

- **现象**：seed5首次校验不一致，差异为一条插入实体的6条quad在全量结果中存在、增量结果中缺失。
- **根因**：`make_new_key`的大偏移量不能保证不同insert之间不撞键——当两条base行主键最后一列恰好相差offset差值时（实测：base 26配j=0、base 25配j=1，都得到1500026），两条插入行共享同一主键。`compute_delta.py`按主键建dict时后者覆盖前者，静默丢行。
- **解决**：插入时维护已用键集合，冲突则递增offset直到新键既不与原始数据也不与已插入键冲突；循环不消耗随机数，随机流不变。重建seed1–4快照逐字节比对确认输出不变（它们本来就没撞键），仅seed5数据变化。
- **代价**：seed5需重跑全量重构与增量更新。

#### 问题11：copytree解引用符号链接，产生陈旧镜像（最隐蔽）

- **现象**：seed5重建数据并重跑后仍不一致，差异表现为"全量结果包含已被删除的行、包含更新前的旧时间值"——全量输出像是**before数据**的映射。
- **排查过程**：字节级检索确认被删行确实不在`after_seed5/stop_times.txt`中；但用秒级的stoptimes专用映射现场重映射该目录，phantom实体依然出现——说明RMLMapper读到的不是我以为的那个文件。追查映射中的`rml:source`实际路径，发现指向`.csv_mirrors/stop_times.csv`，而它是**普通文件而非符号链接**，`diff`确认其内容就是before的`stop_times.txt`。
- **根因链条**：
  1. baseline运行(17:03)在`data/before/.csv_mirrors/`创建了符号链接；
  2. seed5重建(19:47)时`change_generator`的`shutil.copytree`默认`symlinks=False`，把before目录里的符号链接**解引用成普通文件副本**带进了新快照（副本mtime保留为源文件的15:49，即去BOM时刻）；
  3. seed5重跑(20:24)时`normalize_mapping.py`发现镜像已存在就沿用（原代码`if not mirrored.exists()`），RMLMapper静默读到了before旧数据——全程无任何报错。
- **教训**：`exists()`检查只能保证"有文件"，不能保证"是正确的文件"；任何缓存/派生物都必须携带可自愈的失效机制。
- **解决**：`normalize_mapping.py`改为**每次都删除并重建镜像符号链接**；同时手工清空所有数据目录与工作目录下的`.csv_mirrors`。
- **修复后**：seed5第三次全量重构（33:19）与增量更新（2.75s）校验一致。

### 4.5 工具与环境层问题（简录）

除上述实验设计层问题外，过程中还处理了一批工程环境层面的障碍，逐条简录（均已解决并有验证）：

1. **Docker Hub被网络阻断**：`registry-1.docker.io`拉取EOF。改从ECR Public镜像仓库拉取官方镜像后重打标准tag（`public.ecr.aws/docker/library/redis:7-alpine`等）。
2. **compose挂载目录属主**：首次`compose up`时dockerd以root自动创建`dist_work/`，普通用户调度器无写权限——停容器、以当前用户重建目录再重启（bind mount在容器启动时解析路径）。
3. **pkill/pgrep自匹配**：`pgrep -f`与`pkill -f`的模式会匹配到调用它们的shell自身命令行，导致一次误判"进程仍在运行"（轮询读到自己的存活时长）、一次pkill直接杀死所在shell使后续命令未执行。规避：模式加字符类（如`[r]mlmapper`）或改用PID精确操作。
4. **RMLMapper输出文件延迟落盘误判**：RMLMapper在全部处理完成后才写出结果文件，监控循环曾据"输出文件尚不存在"误判长任务失败——判活应以进程存在性为准。
5. **MappingBench误将`-D`传给javac**：javac不接受JVM运行参数，静默无输出；拆分编译与运行参数后恢复。
6. **Dockerfile的javac与运行时classpath遗漏rmlmapper.jar**：worker改为同JVM直调Main类后，编译与运行均需该jar在classpath上，遗漏即编译失败。


## 5. 实验结果与分析

### 5.1 总体结果（表1数据）

| 方法 | 耗时（均值±标准差） | 内存峰值 | 输出quad数 |
|---|---|---|---|
| 全量重构 | **1842.21 ± 102.25 s** | 1130.5 ± 72.3 MB | 375,546 |
| 单线程增量更新 | **2.40 ± 0.22 s** | 未记录（指导已注明该局限） | 375,546 |

各次明细：

| seed | 全量耗时(s) | 全量内存(MB) | 增量耗时(s) | 一致性校验 |
|---|---|---|---|---|
| seed1 | 1738.30 | 1036.0 | 2.39 | 一致 |
| seed2 | 1844.75 | 1111.9 | 2.33 | 一致 |
| seed3 | 1765.11 | 1231.3 | 2.15 | 一致 |
| seed4 | 1863.84 | 1162.8 | 2.15 | 一致 |
| seed5 | 1999.07 | 1110.5 | 2.75 | 一致 |

**加速比约767倍**（1842.21/2.40）。正确性方面，5个seed的增量输出与对应全量重构输出逐行一致，指导第5节的独立verify复核亦通过——增量链路（diff→专用映射→stale IRI→应用）的正确性得到端到端确认。

### 5.2 全量重构的耗时构成

全量重构的约30分钟几乎全部消耗在RMLMapper的join解析上：

- 映射本身涉及约6万行输入、13个TriplesMap，其中`shapes`→`shape_points`的join两侧都是57,474行，朴素实现下是约3.3×10⁹次比较，是绝对的支配项（对照证据：仅保留stoptimes/stops/trips三个TM的小规模映射4秒即可完成）；
- 5次运行的耗时方差（±102.25s，约5.5%）主要来自JVM行为与系统缓存状态，属于正常波动；
- 输出quad数恒为375,546：变更设计是对称的（insert增55×6条、delete减55×6条、update/composite新旧替换净值为0），图规模不随seed变化，符合预期。

值得强调的是，这个30分钟是**映射引擎的实现特征**（朴素join）而非RML语义的必然成本——但这恰恰是增量方法要规避的真实成本，作为表1第一行的基线是诚实的。该归因的分解实验见第6节（T'）。

### 5.3 增量更新的耗时构成

增量的2.40s由四步组成：CSV级diff（毫秒级）、专用delta映射（JVM启动约1.5–2s + 映射167行）、stale IRI拼接（毫秒级）、baseline按subject过滤后拼接（线性扫描375k行，数百毫秒）。

两个结构性观察：

1. **固定成本主导**。2.4s中大部分是JVM启动与Python脚本开销，真正随变更规模增长的部分极小。这意味着在本数据规模下，即使变更比例从10%提高到更高水平，增量耗时的增长也非常平缓——加速比主要由全量侧的成本决定。
2. **复杂度来源不同**。全量的成本核心是"未变更数据也要重新映射"以及映射内部的二次方join；增量把映射范围缩到变更行，且专用映射不含任何join，等于同时消除了这两个放大因子。767倍不是渐进式的优化收益，而是"重算一切"与"只算变化"之间的量级差异。

### 5.4 正确性分析

正确性链条的每一环都有独立证据：

- **专用delta映射 ≡ 完整mapping的stoptimes部分**：逐quad集合比对0差异（问题7的验证实验）；
- **stale IRI与图谱subject格式一致**：编码规则经实测标定，removed计数与理论值严格相等（167×6）；
- **端到端**：5个seed全部通过`sort`+`diff`，且verify独立运行复核通过。

特别说明seed5的三次波折（键冲突→陈旧镜像→最终通过）：前两次失败都不是增量方法本身的缺陷，而是数据生成器与文件适配层的工程bug；这也侧面说明了指导坚持"校验通过才有资格报数字"的必要性——没有第5节的强制校验，seed5的错误数据会被无声地写进论文。

### 5.5 局限性与有效性威胁

如实列出（部分为指导已声明的已知局限）：

1. **变更覆盖面**：当前只有`stop_times.txt`被施加变更，专用delta映射也只覆盖stoptimes实体。若未来扩展到trips/routes等文件，需要为每个受影响实体生成对应的delta映射（`build_delta_mapping.py`已参数化`--target-label`，框架可直接扩展）。
2. **增量内存未计量**：`run_incremental_update.sh`用`date +%s.%N`计时，未像全量那样包`/usr/bin/time -v`，表1如需增量内存数据需补充（指导已预留此说明）。
3. **apply步骤的内存**：`apply_delta_to_graph.py`将整个baseline载入Python列表，375k quad（约66MB文本）无压力，但图规模再大一到两个数量级就应改为流式处理。
4. **join等价替换的前提**：依赖"父表在本实验中不变"。若变更触及父表主键列，需要真正的fan-out算法，当前实现不支持（与指导的原始边界一致）。
5. **单一映射/单一引擎**：结论绑定于该RML映射与RMLMapper 8.1.0的join实现；T'实验（第6节）已直接量化了引擎join实现的贡献——移除单个二次方join后全量基线降至11.07±0.29s，此时增量相对全量的优势缩小到约4.6倍，但方向不变。
6. **外部效度**：单一数据集（马德里地铁，中小规模）。shapes占全图行数的92%，它既制造了全量的二次方瓶颈、又因从不被变更而成就了增量的优势——这一结构特征是否普遍，需要在更多feed上检验。

## 6. 补充实验：T'——若引擎对大表不用朴素join，全量重构要多久

表1的全量基线绑定了RMLMapper的朴素join实现。为了把"RML语义本身的成本"与"特定实现×特定映射形态的成本"区分开，设计了一个分解实验：**保留全部13个TriplesMap和其余11个join原样不动，仅把`shapes`→`shape_points`这一个二次方join替换为等价的模板对象映射**，重新做一次全量重构，记耗时为T'。

### 6.1 与stoptimes案例的关键差异及等价性论证

该join是**一对多引用**：每条SHAPES.csv记录（作为Shape实体）要链接到同shape_id的全部K条记录（作为ShapePoint），单条`rr:template`在子记录上只能发出1个对象，无法逐记录复现K个——不能照搬stoptimes的替换方式。但注意两个事实：两个TriplesMap读的是**同一个文件**（SHAPES.csv），且shapes的subjectMap只由`{shape_id}`决定。于是按RDF集合语义：

- join产生的三元组集 J = {(Shape(S), pred, Point(rⱼ)) : ∀rᵢ,rⱼ∈同文件, rⱼ.shape_id = S}；
- 模板产生的三元组集 T = {(Shape(shape_id(r)), pred, Point(r)) : ∀r}；
- T⊆J 显然（取rᵢ=rⱼ）；J⊆T 是因为rᵢ发出的三元组的subject=Shape(S)与具体哪条行发出无关，恒等于rⱼ自己发出的那条。

∴ **J≡T**（配合RMLMapper对输出quad的去重）。此论证的前提全部在`build_tprime_mapping.py`中强制校验（subject模板变量恰为{shape_id}、两TM同一逻辑源、join标准形式且列=shape_id/shape_id、父模板变量都在CSV表头中、谓词可解析、无其他意外join），任一不满足即退出。数据侧同时核验：57,474行中关键列0空值（30个shape，单shape最多6,684个点）。

### 6.3 分析

1. **单个join占原耗时的99.4%**。1842.21s − 11.07s ≈ 1831.1s 全部归于`shapes`(57k行)→`shape_points`(57k行)的约3.3×10⁹次比较；移除它之后，剩余成本（映射约6万行输入、其余join合计约10⁷次比较、写出66MB输出、JVM启动）平均只有约11秒，且5次波动仅±0.29s（±2.6%）——远小于原基线的±102.25s（±5.5%），因为剩余路径上已没有对缓存与JVM行为高度敏感的二次方循环。
2. **内存几乎不变**（1139.0 MB vs 1130.5 MB）：内存由记录加载与去重结构主导，而非join循环——这也解释了为什么朴素join只拖慢时间不拖慢内存。
3. **对论文的意义**：(a) 表1全量基线的30分钟应如实注明是"朴素join实现×该映射形态"的结果，不是RML语义的固有成本；(b) 它精确解释了增量767倍加速比的主要来源——增量专用映射既缩小了映射范围，又天然不含这个二次方join；(c) 若审稿人质疑基线被人为劣化，T'=11.07±0.29s给出了"理想引擎下的全量"参考值，此时增量（2.40s）相对T'仍有约4.6倍优势，结论方向不变。
4. **方法论注记**：一对多join的模板化替换之所以合法，靠的不是逐记录等价而是集合级等价，其成立依赖"同文件+subject仅由join键决定"这两个可校验前提。任何想把这类替换推广到其他映射的尝试，都应先重跑`build_tprime_mapping.py`中的前提检查。

## 7. 分布式增量更新实验（表1第3行）

### 7.1 架构与实现

按既定架构落地：**1个Redis容器**（任务队列`tasks:queue` + 实体版本号哈希表`versions`）、**k=4个worker容器**（各限1 CPU/1GiB，常驻Java进程，Jedis客户端）、**宿主机纯Python调度器**。数据流：compute_delta产出ΔD→按trip_id哈希(md5)分4区→窄化mapping全局复用一份、normalize每分区一次→任务只传文件路径推入队列→worker领任务后先HMGET记版本快照、映射本分区、EVALSHA单个Lua脚本原子提交（全部key比对通过才统一HINCRBY）→收齐汇报后合并输出，stale计算与apply复用单线程组件不变。

- **实体key用逻辑键`trip_id|stop_sequence`**而非subject IRI：update改变arrival_time从而改变IRI，逻辑键跨update稳定，同一记录的并发更新才能正确撞版本号。
- **RMLMapper调用方式经历了一次由实测驱动的返工**：最初因"无第0步结论"保守地采用ProcessBuilder子进程方式（每任务约1.5s JVM启动）；补做第0步探针实验（见7.2）证实成功路径可安全同JVM复用后，改为worker内直接调`Main.main()`——这一改动把k=4对单线程的劣势（慢38%）直接翻正为优势（快2.43倍）。

最终形态包含两项可靠性加固（均实测验证）：

- **exit-guard**（SecurityManager）：RMLMapper错误路径的System.exit会把worker JVM整个带崩且无法捕获。ExitGuardProbe在JDK 21实测：加`-Djava.security.manager=allow`后guard可安装，System.exit被拦截成可捕获的SecurityException抛回调用方（C标记），合法映射不受影响（916ms正常出图）；无标志时安装抛UnsupportedOperationException（负对照），代码优雅降级为"输入预检+容器重启"。生命周期警告：JEP 486在JDK 24整体移除SM，届时此兜底失效。
- **BRPOPLPUSH + 超时重投**：领取任务即原子转入`tasks:processing`列表并盖`claimed_at`时间戳；worker后台守护线程扫描超过STALE_MS(120s)未完成者重投(attempts+1)。修复过程中踩掉一个并发坑：watcher与主循环共享同一个非线程安全的Jedis实例导致RESP应答串线（双方互相收到对方的类型，ClassCastException成对出现）——watcher改用独立连接后0异常。

工程上踩掉的三个坑：(a) RMLMapper 8.1.0需要Java 21（class版本65），worker镜像最初用temurin 17导致所有任务秒级失败进死信队列；(b) compose首次启动时dockerd以root自动创建挂载目录dist_work，调度器无写权限；(c) 同JVM直调要求Dockerfile的javac与运行classpath都包含rmlmapper.jar，遗漏即编译失败。

### 7.2 第0步探针：Main.main()的退出行为实测

选型不能凭猜，用探针`dist/src/MainExitProbe.java`在主线程上直调`Main.main()`三次（两次合法输入+一次错误输入），以标记行是否齐全判别System.exit：

| 调用 | 标记打印 | 结论 |
|---|---|---|
| 合法mapping #1 | A1✓ B1✓（1122ms） | 成功路径正常返回 |
| 合法mapping #2 | A2✓ B2✓（**136ms**），输出与#1逐行一致 | 可重复调用，类加载只付一次 |
| 不存在的mapping | C✓ 后D/E缺失，exit=1 | **错误路径System.exit(1)，会把宿主JVM带崩** |

由此确定：in-process复用可行但必须防御错误路径——worker调用前预检mapping文件存在、调用包try/catch(Throwable)、compose给worker配`restart: unless-stopped`兜底未预见的内部exit。

**关于seed1=4.84s离群值的成因（已实测定位）**：它是worker常驻JVM的一次性预热成本——RMLMapper fat包(191MB)首次调用需加载/校验/JIT预热数千个类。放大链条逐级实测：裸跑首调1.70s → 单容器`--cpus=1`限流下2.94s → 4容器同时首调并发争抢下3.59~4.09s/个。四worker并行取max≈3.4~4s，叠加调度器固定相位即得4.84s；对照实验复现良好（重建后重跑同负载4.52s，其中wait_workers相位从热态0.23s涨到3.41s、其余相位不变）。该成本每worker生命周期只付一次，跨实验摊销为零——稳态口径（seed2–5）反映的才是部署真实更新成本。

对比返工前后：子进程方案3.32±0.11s（慢38%）→ 同JVM方案稳态0.93s（快143%）。翻转的来源正是被消除的固定成本：k次JVM启动（每次~1.2s）变为一次性类加载，此后每任务的纯映射仅约136ms。这也印证了5.3节的判断——此规模下胜负完全由固定开销决定，谁消除了固定开销谁就赢。

机制正确性不因调用方式改变而受影响：Lua原子提交、乐观并发重试、死信兜底三层证据（单测/强制冲突/日志零异常）全部保持通过；全程0次冲突、0条死信。残余风险如实声明：RMLMapper内部未预见的错误路径可能System.exit带崩某个worker，正在处理的那个任务按BRPOP语义丢失（容器restart拉起后继续服务后续任务）；生产化需BRPOPLPUSH级别的回捞与更完整的输入预校验。



### 7.5 规模外推：纯映射耗时曲线与并行增益的饱和点

为回答"ΔD要多大才能充分体现k=4并行"，用合成数据测了纯映射耗时曲线（同JVM预热后取5次中位数，排除类加载与diff/stale/apply干扰；trip_id加唯一后缀保证实体不塌缩）：

| ΔD行数 | 1,000 | 5,000 | 20,000 |
|---|---|---|---|
| 纯映射中位数 | 144 ms | 385 ms | 1,214 ms |

线性拟合：**T_map(N) ≈ 95 ms + 56 µs × N**（三点预测偏差均<6%，线性假设成立）。

以N=167的实测端点反推流水线固定成本：单线程A_s≈3.01 s（含每次任务的子进程JVM启动~1.25s、diff/stale/apply），分布式稳态A_p≈1.40 s（常驻JVM无每轮启动，含Redis往返与合并IO）。模型在N=167处给出的比值2.16×与实测2.16×吻合，模型可用。由此得到三条推论：

1. **当前架构下不存在"并行更慢"的规模区间**：A_p<A_s 且映射斜率还占1/k优势，任意ΔD规模下分布式都不输单线程——旧子进程方案在167行时慢38%的劣势区已被in-process改造彻底消除。
2. **但增益向理想4×饱和得很慢**：比值(N)=(A_s+56µs·N)/(A_p+14µs·N)。达到3.0×需要ΔD≈8.5万行，3.5×需要≈27万行。
3. **本数据集的天花板太低**：stop_times.txt总共只有2216行，即使change_ratio拉到1.0让ΔD=全表，比值也只从2.15×升到2.19×（+2%）。结论：不是调参问题，是数据集本身不够——要展示接近k倍的并行加速，需要换数十万行级stop_times的大feed（如CRTM巴士网络或多方式合并GTFS），或按40倍量级合成扩充。


### 7.6 规模扩展验证：Urbanos真实大feed（38万行）

纯映射曲线（7.5节）预测并行增益需要大规模ΔD才能显现。为在**真实数据**上验证该预测，接入CRTM巴士城市网络GTFS（`GTFS Red de Autobuses Urbanos`，与metro同一发布渠道下载）：stop_times **382,362行**（metro的173倍），列结构与metro逐列完全相同——mapping零适配；键唯一性、BOM、引用完整性逐项复查全部通过。

**基线构建的线性化推广**：38万行下若沿用朴素join，仅stoptimes→stops/trips、trips→shapes三组就需约117亿次比较（小时级）。将7.5节的等价模板化方法推广到全mapping（新增前提：父模板变量必须能由子记录对应列提供；跨文件join要求零悬空引用），11个join替换、1个保留（trips→services2：trips引用的960个service_id中848个不存在于calendar_dates——GTFS例外语义所致，模板化会产生原语义中没有的链接；保留成本仅236万次评估≈1.3s）。线性化基线**73秒**建成（朴素方案预计小时级），377万quad，峰值RSS 4.3GB。

| stoptimes→stops (38万×8.4k) | 3.21×10⁹ | ≈30 min |

| 其余 | ~8×10⁷ | <1 min |
| **合计（+线性项与启动）** | 5.49×10¹⁰ | **≈8.5 h/次；全套7次≈59 h** |

（费率0.554µs/eval由metro实测标定：1831s÷3.303×10⁹。）

**标定有效性验证（跨数据集泛化，已实测）**：单点标定能否泛化到其他feed？从巴士shapes.txt构造三个5,000行子集——稀疏(随机抽样,匹配密度0.005≈bus总体特征)、中密(整组抽样,密度0.072≈metro等效)、稠密(最大组,密度0.418)——在`--cpus=1`容器内以真实join映射各跑6次取中位数：

| 子集 | evals(N²) | 匹配对M | 中位数 | 混合速率 |
|---|---|---|---|---|
| sparse | 2.50×10⁷ | 1.23×10⁵ | 14,536 ms | 0.581 µs/eval |
| mid | 2.50×10⁷ | 1.80×10⁶ | 12,921 ms | 0.517 µs/eval |
| dense | 2.70×10⁷ | 1.13×10⁷ | 25,208 ms | 0.935 µs/eval |

发现速率并非常数而是匹配密度的函数。两参数最小二乘拟合（物理约束模型）：

**T_join ≈ 0.52 µs × eval次数 + 0.98 µs × 命中对数**

三点残差≤14%；**回代metro锚点预测1900s vs 归因实测1831s，偏差仅3.8%**——远优于20%准则，且解释了机制：0.52µs是纯条件评估成本（跨数据集稳定），额外的~1.0µs/命中对是IRI生成与去重成本（随匹配密度出现）。混合速率对比中sparse/mid与标定值偏差仅+4.9%/−6.7%，dense的+69%由其7倍匹配密度经β项解释而非速率失效。

用该模型重推Urbanos朴素全量重构：evals=5.49×10¹⁰、命中对=2.13×10⁸ → **≈7.98小时**，与单点推算的8.5h偏差<7%——原推算获得实测背书，且得到一个更精细的可外推成本模型（例如Interurbanos的shapes为238万行但匹配密度仅0.001，其朴素join成本应以α项为主重新评估）。

2. 旧表缺少代码版本和环境快照，不能对历史耗时做源码级归因。通过逐字节比对确认本次普通生成输入与旧标准输入一致，并在同一当前会话内重跑五组配对任务；仍观察到跨会话时间差，故将其作为测量限制，而非归因于未经验证的代码变化。
3. 首次分布式调度受本机沙箱socket权限限制，无法连接本地Redis；获准在实验权限下重跑同一命令后完成，五组任务均正常结束，图数据校验通过。

## 8. 消融实验（表2：机制消融）

### 8.1 设计前提：为什么必须注入冲突

按entity(trip_id哈希)分区天然不产生跨worker的真实冲突——若直接在无冲突delta上对比A0（完整方法，乐观版本号）与A2（全局锁），两组输出完全相同、协调指标全为0，测不出机制差异，甚至可能因版本检查的微小开销得出"一致性机制没必要"的错误结论。因此本实验的前提是**调度阶段人为注入冲突**：以可调比例把ΔD行随机复制进相邻分区，使两个worker的实体key列表必然重叠（模拟并发改同一记录）；固定随机种子42保证A0/A2两轮注入完全一致。复制导致合并前delta含重复quad，merge阶段按行去重保证图谱正确。

三组配置：**A0**完整方法（实测）；**A1**关闭并行调度＝单线程串行（复用u50档数据38.98±1.75s，不重跑）；**A2**全局锁模式（worker以`CONSISTENCY_MODE=lock`部署）。规模选u50档；每配置×每冲突率{0%,5%,20%}×5 seed。指标分列：A0记**冲突重试次数**，A2记**锁等待时间/竞争次数**。公平性细节：映射不受锁保护（只对比提交阶段策略）；映射是输入的纯函数，A0重试跳过重复映射仅重做提交；两轮注入同种子。

**时序对齐问题与提交栅栏（关键设计迭代）**：首轮实验发现，尽管键重叠已注入，全局锁的竞争次数仍为0——worker日志的毫秒级时间戳显示，四个worker的LOCK-TRY时刻两两间隔最小约353ms：各分区映射时长不同，提交瞬间天然错开。而OCC侧同场景却稳定检出2次重试——**两种机制的冲突检测窗口宽度本质不同**（OCC覆盖从版本快照到提交的整个任务时长，秒级；全局锁只在提交瞬间，毫秒级）。修复：引入Redis提交栅栏——各worker映射完成后INCR就绪计数，全员到齐才同时放行进入提交阶段。栅栏后同一负载下四个LOCK-TRY全部落入2ms窗口、产生5次自旋失败——竞争被真实触发，下述结果均为对齐后的正式测量。

### 8.2 结果（Urbanos u50档，k=4，交错配对测量，各5轮）

首轮矩阵按c0→c5→c20顺序串行执行，得到"锁模式耗时随冲突率单调下降"的反直觉趋势。排查发现这是**宿主性能漂移混杂**：compute_delta相位（三档完全相同的工作量）作为示踪剂显示宿主在该时间窗内从慢速窗口逐步进入快速窗口（极差40%），而矩阵执行顺序恰好与之共线。修正设计为**交错配对测量**——c0与c20背靠背交替执行（同快照、同种子注入），使两档经历相同的宿主状态：

| 冲突率 | A0(OCC)耗时 | A0重试合计 | A2(全局锁)耗时 | A2等锁总量 | A2竞争次数 |
|---|---|---|---|---|---|
| 0%（对照） | 14.63 ± 0.82 s | 0 | 14.34 ± 0.90 s | 8 ms | 0 |
| 20% | 16.96 ± 0.34 s | **10**（每轮恰2次） | 16.14 ± 0.33 s | 139 ms | **11** |

全部20次运行的输出与单线程增量结果`sort`+`diff`逐一一致。竞争真实性证据链：栅栏前四个LOCK-TRY时刻两两间隔最小353ms（零FAIL）；栅栏后全部落入2ms窗口并产生自旋失败——冲突注入在时间维度上真正生效，且c0对照组零竞争证明失败来自键重叠而非栅栏本身。

### 8.3 分析（基于交错配对测量的最终结论）

1. **冲突率0%（对照组）**：两机制端到端耗时统计等同（锁/OCC=0.98，±1σ重叠），协调事件均为零——干净基线成立。
2. **冲突率上升使两机制都变慢，幅度相当**：OCC +15.9%、锁 +12.5%。分解后可见增量主要来自注入的重复工作量本身（映射量与去重量同步增长，两法均摊）；机制自身的协调成本占比很小但方向明确。
3. **结构性指标的确定性分离**（比端到端耗时的信息量大）：A0的重试数由"含共享键的任务对数"结构性决定（每轮恰2次、5轮完全一致）；A2的等锁总量与竞争次数随冲突率单调增长（8ms→139ms、0→11次）。两种机制的**行为特征差异真实存在且可精确测量**。
4. **机制间端到端差异处于噪声边缘（锁/OCC=0.98@c0、0.95@c20）**：原因在于协调成本（百毫秒级）被两个大得多的共同项稀释——秒级映射与图谱规模相关的apply阶段（约10–13s）。因此**在本实验的规模与任务粒度下，不能宣称哪种一致性机制整体更优**；"哪种机制更划算"的分化需要协调成本占主导的场景（更多worker、更细任务粒度、更大冲突密度）才会显现。
5. **对初版过度表述的两点修正**：(a) 初版"并行价值稳健……不依赖一致性机制选择"建立在无真实竞争的数据上；(b) 中间一轮曾出现"c20时锁反超26%"，同样被证实为漂移假象（OCC的c20档恰运行于宿主慢速窗口）。最终受控结论：**两机制表现等同；并行调度相对单线程的收益稳健（1.92–2.42×）**。
6. **局限（如实声明）**：(a) A0重试粒度为整个分区任务，实体级细粒度重试会改善其高冲突表现；(b) 行复制语义未覆盖"同一实体收到不同新值"的真写写冲突变体；(c) Redis SET NX锁非FIFO公平；(d) OCC的版本快照(HMGET)与原子比对(EVALSHA)在u50分区规模实测约171ms+124ms——该成本随实体key数量线性增长，超大规模下将成为OCC特有的额外负担。

## 9. 结论

在CRTM真实GTFS数据、10%变更比例、5个独立seed的设置下：

- 全量重构平均耗时**1842.21±102.25 s**、内存**1130.5±72.3 MB**；
- 单线程增量更新平均耗时**2.40±0.22 s**，加速比约**767倍**；
- 全部5个seed的增量输出与全量重构逐quad一致，方法正确性得到端到端验证；
- 分布式增量更新（第7节，k=4，worker同JVM复用RMLMapper）最终轮稳态耗时**1.40±0.05 s**、含冷启动原始均值2.09±1.54 s，较单线程分别快2.15倍/1.44倍；
- 规模扩展验证（第7.6节，真实巴士feed 38万行）的历史测量曾报告稳态比值1.63×→1.73×→2.09×；第7.7节复核发现10%档存在跨会话耗时漂移、旧表统计口径不一致，故该历史趋势目前不作为与本次倾斜矩阵直接合并的论文结论。端到端比值受图谱规模相关共享成本稀释的相位分析仍成立，但需统一会话与统计口径后再确定最终绝对值；
- 分区倾斜实验（第7.7节，Urbanos 10%档、k=4）中，实测倾斜因子吻合理论，分区映射耗时差随p从约0.23秒增至1.87秒；端到端加速比在本规模下没有单调趋势。p=0与普通标准生成路径不是相同变更样本，因此该实验只支持“映射层负载倾斜增大”的结论，不能把p=0替代标准10%基准；
- T'方法在大规模下从"分析工具"升级为"唯一可行的基线获取手段"：Urbanos上朴素全量重构推算需8.5h/次（全套59h不可行），T'式实测仅63.42±5.93s（482倍差距）；且即使按可行的T'基线计，50%档单线程增量（38.98s）仍快于全量重构，分布式增量（18.68s）再快2.1倍——核心论点在真实大规模数据上成立、较原始全量约1981倍，输出与单线程逐一完全一致：并行架构与轻量一致性机制（论文4.4节）得到端到端验证；
- 分解实验（第6节）表明：仅把`shapes`→`shape_points`这一个朴素O(n²) join替换为可证等价的模板，全量重构即从1842.21±102.25s降至11.07±0.29s（5次独立运行）——原基线99.4%的耗时来自引擎的join实现而非RML语义本身；
- 分布式增量更新（第7节，k=4）耗时**3.32±0.11 s**，输出与单线程增量逐一完全一致：Redis任务队列+实体版本号乐观并发+失败重试的并行架构与轻量一致性机制（论文4.4节）得到端到端验证。在此规模下并行慢于单线程约38%，系ΔD仅167行、固定成本主导所致——如实报告，加速价值留待大规模数据检验。

实验的主要工程量在于让指导脚本的前提条件在真实数据上成立：文件名/BOM/扩展名适配、join结构的规范性核验、增量链路的重复quad与性能缺陷修补，以及三个隐蔽bug（IRI编码、主键冲突、陈旧镜像）的定位与修复。其中"陈旧镜像"一例表明：在引入任何"派生物缓存"时，必须设计成可自愈的，否则会在毫无报错的情况下污染实验结果——本次正是依靠强制正确性校验才将其拦截在报告数字之外。
