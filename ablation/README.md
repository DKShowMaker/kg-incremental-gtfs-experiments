# 消融实验（表2：机制消融）

对应表2设计：完整方法(A0) / 关闭并行调度(A1) / 关闭轻量一致性机制改全局锁(A2)。

## 0. 前提认知：为什么必须注入冲突

按entity(trip_id哈希)分区天然不产生跨worker的真实冲突。若直接在无冲突delta上对比A0与A2，两组输出完全相同、冲突/等待指标全为0——测不出两种机制的任何差异，甚至可能因版本检查的微小开销让A2"显得更快"，得出错误结论。因此**冲突注入是本实验成立的前提**：调度阶段人为把一定比例的实体key复制进相邻分区，模拟"两个worker同时改同一记录"，冲突率作为可调参数扫描{0%, 5%, 20%}。

## 1. 三组配置

| 组 | 配置 | 数据来源 |
|---|---|---|
| A0 | 完整方法（乐观版本号OCC） | 本实验实测 |
| A1 | 关闭并行调度＝单线程串行 | **复用**单线程增量基线数据（u50档38.98±1.75s），不重跑 |
| A2 | 关闭一致性机制，改全局锁 | 本实验实测（CONSISTENCY_MODE=lock） |

## 2. A2实现要点（概念）

- 映射计算(RMLMapper)不受锁保护，各worker照常并行——锁只在提交动作上生效，公平对比"提交阶段并发度"；
- 锁用Redis原语`SET NX EX`自旋获取、用完DEL释放（排他、阻塞式获取、用完释放）；
- 指标替换：全局锁没有"冲突重试"概念，记录**锁等待时间**与**锁竞争次数**；与A0的**冲突重试次数**分开列报，不可混列。

## 3. 正确性

冲突注入会使合并前的delta含重复quad（同一行被两个worker各映射一次），merge阶段按行去重保证最终图谱正确；每个配置每个冲突率的输出都必须与单线程增量结果逐行diff一致——A2不因A0验证过而豁免。

## 4. 规模与口径

只做u50档（已证明并行收益最大的规模）。每配置×每冲突率5次重复；区分稳态/含冷启动口径（首轮含worker重建后的类加载预热时单独标注）。冲突注入随机种子固定42，A0/A2两轮完全一致以保证可比。

## 5. 预期方向（跑完自查）

- 冲突率0%：A0应不慢于A2——全局锁即使无真实冲突也强制所有提交串行排队（排他语义不区分实体），乐观版本号允许不同实体真正并发提交；
- 冲突率上升：A0的重试次数上升，A2的锁等待时间上升；吞吐量谁先崩是实验要回答的问题；
- 若趋势与预期相反：先排查实现（锁粒度/退避策略），确认非实现漏洞后才可作为发现写入论文。
