# 消融实验（表2：机制消融）

对应表2设计：完整方法(A0) / 关闭并行调度(A1) / 关闭轻量一致性机制改全局锁(A2)。

## 0. 前提认知：为什么必须注入冲突

按entity(trip_id哈希)分区天然不产生跨worker的真实冲突。若直接在无冲突delta上对比A0与A2，两组输出完全相同、冲突/等待指标全为0——测不出两种机制的任何差异，甚至可能因版本检查的微小开销让A2"显得更快"，得出错误结论。因此**冲突注入是本实验成立的前提**：调度阶段人为把一定比例的实体key复制进相邻分区，模拟"两个worker同时改同一记录"，冲突率作为可调参数扫描{0%, 5%, 20%}。

## 1. 三组配置

| 组 | 配置 | 数据来源 |
|---|---|---|
| A0 | 完整方法（乐观版本号OCC） | 本实验实测 |
| A1 | 关闭并行调度＝单线程串行 | **复用**历史单线程基线（u50档seed1–5：38.98±1.75s），不重跑；仅作参考，不与A0/A2跨会话计时求加速比 |
| A2 | 关闭一致性机制，改全局锁 | 本实验实测（CONSISTENCY_MODE=lock） |

## 2. A2实现要点（概念）

- 映射计算(RMLMapper)不受锁保护，各worker照常并行——锁只在提交动作上生效，公平对比"提交阶段并发度"；
- 锁用Redis原语`SET NX EX`自旋获取、用完DEL释放（排他、阻塞式获取、用完释放）；
- 指标替换：全局锁没有"冲突重试"概念，记录**锁等待时间**与**锁竞争次数**；与A0的**冲突重试次数**分开列报，不可混列。

## 3. 正确性

冲突注入会使合并前的delta含重复quad（同一行被两个worker各映射一次），merge阶段按行去重保证最终图谱正确；每个配置每个冲突率的输出都必须与单线程增量结果逐行diff一致——A2不因A0验证过而豁免。

## 4. 规模与口径

只做u50档。A0/A2在每个冲突率下各重复5次；区分稳态/含冷启动口径（首轮含worker重建后的类加载预热时单独标注）。冲突注入随机种子固定42，A0/A2两轮完全一致以保证可比。A1复用的是未注入冲突的历史单线程基线，不是本矩阵的同会话配对计时；c5/c20复制行会增加映射工作量，故不得用A1计算这些档位的并行加速比。

## 5. 预期方向（跑完自查）

- 冲突率0%：A0应不慢于A2——全局锁即使无真实冲突也强制所有提交串行排队（排他语义不区分实体），乐观版本号允许不同实体真正并发提交；
- 冲突率上升：A0的重试次数上升，A2的锁等待时间上升；吞吐量谁先崩是实验要回答的问题；
- 若趋势与预期相反：先排查实现（锁粒度/退避策略），确认非实现漏洞后才可作为发现写入论文。

## 6. 固定映射工作量的分区倾斜实验

本实验单独测量哈希分区不均对并行映射的影响，不启用冲突复制。使用 Urbanos 的 10% 变更档，`insert + update + composite` 产生固定的约 28,677 行映射 ΔD；`delete` 不计入映射工作量，也不参与定向倾斜。

生成器和调度器共同调用根目录 `partitioning.py` 中的 MD5 `trip_id % k` 函数。生成器把恰好 `round(p*M)` 个映射事件定向到哈希分区0，按 insert/update/composite 的事件数用最大余数法分摊；剩余事件仍从数据行均匀抽样。生成器在每个快照内写入 `.partition_skew.json` 清单，调度器会拒绝与生成时不同的 k，并校验实际 ΔD 行数。均匀抽样也可能自然命中分区0，因此理论倾斜度为 `s=1+(k-1)p`，实测值用 `s=k*partition_0_rows/partition_rows` 计算。每档 ΔD 实际行数必须相同，汇总器会校验这一点。

每个分区行数、各分区映射耗时、Worker 标识和完成时间写入 `time_distributed_<tag>.log`。映射时长差是各分区 `mapped_ms` 的最大值减最小值；完成时间差则按 Worker 的 Unix 毫秒时间戳计算，二者都保留，便于区分任务耗时与排队/启动偏移。

先按实验的 k 启动同样数量的 Worker；改变 k 后必须重新生成倾斜输入，矩阵脚本会将 k 同时传给生成器和调度器：

```bash
docker compose build worker
docker compose up -d --scale worker=4
bash ablation/run_skew_matrix.sh
```

矩阵为 `p={0, 0.25, 0.5, 0.75, 1}` × `seed={1..5}`，逐档配对运行单线程与分布式更新。每档首个 seed 保留原始数据但不纳入稳态汇总。结果写入 `results/skew_raw_k4.csv` 和 `results/skew_summary_k4.csv`。脚本遇到已存在的本矩阵输出会停止，避免覆盖已有数据。若改用其他 k，例如 `K=8 bash ablation/run_skew_matrix.sh`，需先以 8 个 Worker 启动 Compose；新 k 会生成独立输入目录。

**对照解释限制**：p=0走倾斜生成器的专用分支，虽然抽样仍均匀，但随机数调用顺序不同，故同seed变更行与普通10%生成路径不同。p=0仅是本倾斜矩阵内部对照，不能与历史标准10%记录按逐seed完全同样本比较。2026-10的标准路径复核及两者差异见`docs/实验报告.md`第7.7节；在统一生成样本并复测前，不把历史扩展表和倾斜矩阵解释为同会话可比结果。
